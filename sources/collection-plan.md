# 来源采集面、唯一性原则与存量审计计划

本文件定四件事：**每条内容的采集面要扫多宽**、**一条内容只许存在一份**、**库的内容要够丰富够专业且覆盖全域**、以及**已有的 266 个条目怎么逐批补缺**。主规划 7.1 定来源优先级、7.2 定单条内容的工作流，本文件定采集面的宽度、唯一性约束、质量底线与存量推进的批次，四者互补，不重复。

写作前提仍是主规划 7.2 的那句话：先归档来源，再写成果。本文件不改变这个顺序，只扩大第一步的范围，并加两条第二层的约束（唯一性、质量底线），以及一条次序原则（库优先、网站派生）。

**全书的次序**（第〇之二、〇之三节展开）：

```
搜（七层，宁滥勿缺）→ 辨（reliability＋rights 两轴）→ 整理（摘录、比对、并列矛盾）
→ 成库（唯一、丰富、专业）→ 主题清单无遗漏 → 库建完美 → 按主题派生网站
```

六步的可操作版本见第〇之三节「六步作业流程」；第 2 步「辨可信度」的三级判据见 `sources/rights.md`「可信度分级」。

## 〇、唯一性原则：一处所一条目，一站一视图

这是 2026-09-29 新增的最高约束，排在所有内容规则之上。

**内容库是唯一的真源。一处所（一个地点、一项物、一件事、一个人物）在本库只能有一条条目。** 各分站网站不另建内容，只从这一条里按本站主题**取用所需的部分**。

理由不是偏好，是本轮量出来的代价：

| 现象 | 实测 |
| --- | --- |
| 同一 slug 在两个站各有一条 | **2 组**：骆山村、上庄村（文化站 `places/` 与街镇站 `villages/` 各一份，**连 slug 都相同**） |
| 同一处所跨站条目 | address 相同的跨站组合 **9 组**，其中「洪蓝街道无想山」一家就有 3 条、「洪蓝街道」有 3 条 |
| 同一 id 在两站重复 | `ls:place:luoshan-village`、`ls:place:shangzhuang-village` 两组 |

重复的真实损害不是「难看」，是**两份都不完整**。骆山村一例：

- 街镇站那份引 3 份来源（区划页、答复、融媒体），写名录归属与区划对照，但**大龙的级别与非遗信息一概不写**；
- 文化站那份引 3 份来源（国家级项目页、民俗风情页、答复），写大龙与舞龙场面，但**没有区划来源**，村落本身的沿革反而最薄。

两份各自都可信，合起来才是这一处的全貌；而**合起来的代价是两处都要各自再查一遍，且必然漏**。这就是「一处所一条目、这唯一的一条尽量写全」的由来：**全，要写在同一处，不许分散在两个站各写一半。**

**2026-09-30 已按此原则合并三组**（骆山村、邰村归街镇站，石臼湖归山水站），文化站 6 份重复条目（中英各 3）已删除，四站条目合计由 530 条降至 524 条。合并中发现两处规则与现实不符，已一并修掉：

1. **`place_ref` 未放行跨站**。引擎的 `related` 早已放行跨站（2026-09-29），但文化站规则的 `place_ref` 仍判错，导致「骆山大龙的流传地归街镇站」后 `place_ref` 指向本街镇站的条目即报错。合并必然逼出这个问题：项目的发生地归口到另一站是常态，不是缺陷。已改为与 `related` 同口径放行。
2. **合并后须留迁移痕迹**。旧 id 停用（`ls:place:taicun` → `ls:place:taicun-village`、`ls:place:shijiuhu` → `ls:place:shijiu-lake`）而不新造 id，是为了让各站 `related` 的指向一次改对；但旧 id 只存在于合并说明里，**必须写进条目正文**，否则后人无从判断某条 `related` 是笔误还是迁移遗留。

### 三条派生规则

1. **一条写全。** 唯一的那条要把该处所在本库的**全部**已核事实写进去，不按站裁剪。分站差异不体现在「写不写」，体现在「取哪段」。
2. **分站按主题取用，不另立条目。** 站有主题分类，视图层按主题字段（`tags` 等）从全量条目中投影出本站该显示的部分，而不是各站维护自己的一份。
3. **发现重复即合并，不新开。** 写任何条目前先搜同 slug、同 id、同 address、同坐标；命中即视为同一处所的既有条目，补它，不新建。

### 「一处所」的边界要先定，否则合并会做错

不是所有相似都该合并。三类判据分开用：

| 判据 | 说明 | 例 |
| --- | --- | --- |
| **同一对象**（该合并） | 同一处所的不同侧面，合为一条 | 骆山村的文化面与街镇面；石臼湖在山水站与文化站各一条 |
| **同一对象的不同实体**（**不该**合并） | 同一地点但对象不同，是两件事 | 「红色李巷」（村落整体）与「李巷革命遗址建筑群」（文保单位）——区文旅局答复已明言文保身份指建筑群、纪念地指村落与旧址整体 |
| **同名异实**（**不该**合并） | 名称相同而对象不同 | 「东庐山」的景点与行政区划；异名不合并（傅氏祠堂/傅氏宗祠） |

**判据是「读者会不会以为这是两处」，不是「字段像不像」。** 合并前先问：两条并作一条，是否会让任一处的事实被压缩变形。会，则不合。

### 落地还差一层结构（本次只记，不急做）

现状是 `content/<siteId>/` 下按站分目录，条目本身带 `site` 字段，**「一条」与「一站」绑死**，所以唯一性只能靠人守。要真正落地，需要把「条目」与「站点视图」拆开：

- 条目不再属于某站，只属于本库；`site` 字段退化为「首发站」或取消；
- 新增一层站点配置（哪一站取哪些 `tags`、哪些 `type`、哪几个小节）；
- 校验器增加**唯一性检查**：同 slug／同 id／同 address／近重复标题跨站出现即报警。

这层结构改动大，属下一阶段；本轮先把原则、判据与合并清单写进计划，并**停止产生新的重复**。

## 〇之二、三条质量底线：丰富、专业、全域

2026-09-29 复审时补入。前一版计划只管「来源够不够广」与「有没有重复」，**没有管「写得多不多、干不干、覆盖得全不全」**——这三样恰是库要「完美」的实质。三条各自给出可量的现状与判据。

### 一、丰富：不是字数，是该有的维度不缺

**定义：一条 `full` 条目要把该对象的七个维度都写过一遍**，缺哪一维就明写「本库未获」，不靠别处凑字数。七个维度：

| 维度 | 内容 | 现状（full 仅 43 条，16%） |
| --- | --- | --- |
| 1 身份 | 名称、别称、位置、所属 | 基本齐 |
| 2 来历 | 始建、沿革、纪年 | 较好 |
| 3 形制 | 形制、尺寸、结构、材料 | **普遍缺**（水库、圩闸、山体多无官方尺寸） |
| 4 制度 | 级别、批次、公布文号、保护范围 | 较好，但批次年份时有「待核」遗留 |
| 5 人物 | 建造者、主持者、传承人 | **薄弱**（题刻类只有「相传」） |
| 6 生活 | 用途、岁时、习俗、传说 | 中等 |
| 7 限度 | 存疑之处、未获项、来源层级 | 本轮已普遍补上 |

**判据：**「丰富」不是把 300 字写成 600 字，而是**七个维度逐一有交代**。正文长度只是副产品。

现状实测（266 条中文稿）：

| 长度 | 条数 | 说明 |
| --- | --- | --- |
| < 300 字 | **2** | 过薄，须优先补 |
| 300–600 字 | 55 | 多为街镇站行政区划条目 |
| 600–1000 字 | 88 | 主体区间 |
| 1000–2000 字 | 87 | 较好 |
| ≥2000 字 | 34 | 上庄与文化站部分条目 |

`depth: full` 仅 **43 条（16%）**，223 条仍为 `standard`。**下一步的「丰富」目标是把 `full` 从 16% 推到大部分**，而不是把 `standard` 拉长字数。最薄的 12 条（<400 字）已列在本节末尾的「最薄的 12 条」表内，作为补写的第一批。

### 二、专业：可核查，而不是显得权威

「专业」不是文风，是**读者能顺着核查**。四条硬要求：

1. **每个事实能落到一张卡的 locator**。做不到就不写。
2. **来源层级必须显形**。转录用网络转录的学术文献与古籍，须标「据网络转录，未核点校本纸面」；媒体须标「二手报道」；弱来源须在正文与 `note` 双处标明。
3. **矛盾并列不取舍**，并降 `confidence`。这一条本库做得最好，须保持。
4. **专名一致**：中英标题的 glossary 专名对应；新专名入词表，不自行塞 `glossary.csv`。

**现状与缺口。** 本库专业度的短板不在写法，在**著录本身**：

- **全库均为网络转录**，旧志无一核到点校本纸面或国图影印。这是最大的专业性欠账，须在每条写明限度（已部分做到），并把「核到影印本」列为长期任务。
- **`confidence` 分布**：全库 `high` 88 条、`medium` 177 条、`low` 1 条（2026-09-29 实测）。`low` 的 1 条经复查认定为诚实值（见第四节）。
- **学术与古籍卡 56 张**，相对 266 条条目仍偏薄；本轮已建卡的著录见第一节末，**大部分尚未落到具体条目上**。

**新增一条自我要求：凡引二手转录而未核原件，卡内 `note` 必须写明「未核纸面/影印」。** 这一条本轮执行到位，是专业度的底线。

### 三、全域：不遗漏任何与溧水相关的重要对象

前两版计划都是**按站、按条目**推进的，从未回答「**该有的对象有没有**」。全域覆盖要一张**主题清单**，逐类确认「有 / 无 / 不适用」，无的要立项，有而薄的排进补写队列。

按标签实测，132 种标签的分布极不均衡——`行政区划` 48 条、`明代` 43 条、`山水` 37 条、`非物质文化遗产` 34 条，而**许多重要主题只有 1–3 条**。这说明库已覆盖传统主线（沿革、文保、非遗、村落、山水），但**若干当代与制度性主题近乎空白**：

| 待审主题 | 现状 | 建议 |
| --- | --- | --- |
| **当代产业与经济**（草莓、螃蟹、蓝莓、茶、影视等） | 标签仅见草莓 3、梅花 3，条目多为节庆或线路 | 溧水的农业与文旅产业是当代内容主线，须独立立项 |

## 〇之三、库优先，网站派生：先把库建完美，再谈网页

这是整份计划的**次序原则**，2026-09-29 复审时明确写入。

**内容库是产品，网站是视图。** 顺序只有一条：

```
来源归档 → 库内条目（一处所一条，写全、专业） → 库的整体完备 → 派生网站（按主题投影）
```

四条推论：

1. **不得为凑网页而写条目。** 反过来做——先有页面再填内容，必然出现薄条目与重复条目。本轮实测已有 2 条不足 300 字、223 条仍是 `standard`，就是这种倾向的后果。
2. **网站不生产内容。** 网站的分类、标签、索引、专题页全部从库里取；库里没有的，网站上也就不该有。想在网站上加一篇，必须先在库里立条并补足来源。
3. **「库建完美」有客观标志，可检查**：七层来源对目标对象已扫过（已核到著录的学术与古籍线索基本落条）；跨站重复归零；全域主题清单无「应建未建」；`depth: full` 成为多数；每条都能顺着 locator 核查到来源层级。
4. **网站可以增，不可以另立门户。** 将来开新站（如人物站、产业站、方言站）是在库里增设**投影规则**，不是在库里增设分区。

**这条与第〇节的唯一性是一件事的两面**：一处所一条条目，是「库」的完整性；库建完派生网站，是「库」的可用性。前者保证不重不漏，后者保证成果能被浏览到。

### 六步作业流程：搜 → 辨 → 整理 → 成库 → 分站 → 留痕

第〇之三是次序原则，这里是它的**可操作版本**，每一步都有产出物与验收条件。六步是流水作业，**每条内容都从头走到尾，六步的痕迹全部留存**。

| 步 | 做什么 | 产出物 | 验收条件 |
| --- | --- | --- | --- |
| 1 **搜** | 按七层采集面穷尽检索，宁滥勿缺 | 候选来源清单 | 七层**每层都过**，含「查过没有」的记录 |
| 2 **辨** | 判定可信度与授权 | `reliability` + `rights` + `note` | **两轴都填**；`tertiary` 写明弱在哪；转录标明未核纸面 |
| 3 **整理** | 摘录、比对、发现矛盾 | 摘录要点、矛盾清单 | 每条摘录可回溯原页；矛盾**并列不取舍** |
| 4 **成库** | 写 Markdown 基础数据 | 条目 + 来源卡 | 一处所一条；七维写全；中英成对；校验 0 错 0 警 |
| 5 **分站** | 按主题投影出站 | 各站页面 | 站内取用不另立；同一处所各站一致 |
| 6 **留痕** | 记录全过程 | `note`、存疑节、`accessed` | 读者能顺着 locator 查到原件；未获项显式写明 |

**两条贯穿六步的纪律**：

1. **搜与辨不可颠倒，也不要边搜边下结论。** 先把候选收齐再逐张判可信度。边搜边判断会导致「先信了再找支撑」——本库已吃过这个亏：D 批给万历十六年凤贤圩补的第二来源是南宋《景定建康志》，但那只能证明**圩为旧有**，不能证明**该年修筑**，两者是不同的事；若不加分寸，就会拿「地名早就存在」当「这件事有旁证」，把 `confidence` 抬起来。所以补来源时必须问一句：**这条材料证明的是这件事本身，还是只与它相关？**
2. **留痕不是最后一步，而是每一步同步做。** 来源一建卡就记 `accessed` 与关键表述；判可信度就写 `note`；发现矛盾就写进条目存疑节。**事后再补的痕迹是补不齐的。**

**六步与本计划各节的对应**：第 1 步见第一节七层；第 2 步的 `reliability` 见 `rights.md`「可信度分级」；第 3 步见第一节三条纪律；第 4 步见第〇、〇之二节；第 5 步见本节与第〇节「一站一视图」；第 6 步是 `rights.md` 硬规则 3 与 4。

### 关键修正：单引条目这个口径一开始就算错了

A、B、C 三批都在按「`sources:` 字段里的 `ref` 条数」数单引条目，这个口径**把同一张卡的多个 locator 算成了多份来源**。D 批开工前重算，真相是历史站有 **26 条**只挂 `src:kangxi-lishuixianzhi` 一张卡（多的带三四个 locator），而按旧口径它们看起来都有三份以上来源、字段完整、状态 published，**读者无法交叉验证却看不出来**。

**教训：数来源必须按去重后的 `src:` id 计，不能按 `ref` 出现次数计。** 台账目前统计的是「引用次数」，同样会高估，改台账口径时应一并改为按去重 id 统计每站的来源份数。A、B、C 三批的「单引归零」结论按新口径重看并不成立，故 D、E 两批以此为准。

### 单条的审计动作

5. 待补项是否还准确，还是已经过时？

## 三、推进纪律

1. **一批做完再做下一批**，不并行铺开。并行会让前一批的问题没查清就带进下一批。
2. **每批结束提交一次**，出问题好回退。
3. **改条目前先查重。** 同一 URL 已有卡的直接复用，避免同一页面两张卡；本轮已因此删过三张重复卡。**另须查同一处所是否已有条目**：同 slug、同 id、同 address、近重复标题命中即视为既有条目，补它，不新建（见第〇节）。
4. **改文件不要用 PowerShell 的 `Set-Content -Encoding UTF8`。** 它会写 BOM，导致 front-matter 解析失败、条目被校验器漏数（本轮踩过，四个条目一度从计数中消失）。批量改文件用 `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。
5. **中英成对。** 任何一侧改动，另一侧同步；`related` 引用的 id 必须真实存在，校验器会逐条核。**`related` 可跨站**（2026-09-30 起放行，渲染为目标站绝对外链）；指向不存在的条目仍判错。旧 id 因合并停用时须在正文写明迁移关系。
6. **宁缺毋滥。** 检索三遍无果就写「本库未获」，不靠推测填充。
7. **推送失败先分辨是哪一类，再决定重试策略。** 本轮连踩三种，症状不同、处置也不同：
   - `SSL certificate ... unable to get local issuer certificate`：**证书链问题**，git 默认 openssl 后端找不到 CA 根证书。加 `-c http.sslBackend=schannel` 走 Windows 系统证书库即可（改仓库配置不如改命令行，不影响他人）。
   - `Recv failure: Connection was reset` / `Failed to connect ... after 21051 ms`：**网络层问题**，换后端解决不了，只能重试。`Test-NetConnection github.com -Port 443` 可先探端口，避免盲目重试。
   - 重试用 `for` 循环 + 递增等待即可，但**注意 PowerShell 里 `"attempt $i: xxx"` 会把 `$i:` 当成驱动器引用而报语法错**，须写 `${i}`。这是本轮实际踩到的一个纯语法坑。

### 关于 `confidence: low` 这一项：目标本身定错了

1. 康熙《溧水县志》卷十一艺文志只作**书目式著录**（「自溧水道中哭王炎三首 李 白」），旧志编者收录不等于判定写诗地点。
